- 但是加入不进去（无法进入对方的房间）

## 根因：两边 mod 构建不是同一个

通过日志前缀和文件 md5 比对确认：

| 文件 | 大小 | md5 | 日志前缀 |
| --- | --- | --- | --- |
| 我原来的 `Mods\WorldLink.dll` | 51712 | `6ab1bc4d…` | `[WorldLink]` |
| 上游 MewoLab 发布的 WorldLink.dll | 51712 | `6ab1bc4d…` | `[WorldLink]` ← 与上完全一致 |
| 朋友用的（NyanLink 官方构建） | 50176 | `9dfa62d5…` | `[NyanLink]` |

判定依据：NyanLink 源码 `mod/BuildInfo.cs` 里 `public const string Name = "NyanLink";`，
即**官方构建的日志标签是 `[NyanLink]`**，朋友那份日志正是这个标签。

也就是说：**我用的是上游 MewoLab 的 mod，朋友用的是 NyanLink 分支的 mod，而服务端是
NyanLink 分支的服务端。** 招募列表走的是 HTTP JSON，两边都能解析，所以弹窗正常；
但加入房间用的是分支改过的二进制协议（`FutariPatch.cs` / `FutariClient.cs` /
`FutariTypes.cs` 都被 fork 修改过），构建不一致就对不上。

## 第二个根因：AquaMai 的 ForceAsServer 抢了 IsLanAvailable

换完 DLL 之后招募能互相看到，但**选曲界面里没有「店内マッチング」分类**，因此找不到
加入入口。原因是 AquaMai 的 `[GameSettings.ForceAsServer]`（默认开启）和 NyanLink
的 mod 在抢同一个属性：

| 模块 | 补丁 | 效果 |
| --- | --- | --- |
| AquaMai `ForceAsServer` | `AMDaemon.Network.IsLanAvailable` | 强制 `false` |
| NyanLink mod | `AMDaemon.Network.IsLanAvailable` | 强制 `true` |

两个 Prefix 打同一个 getter，谁最后生效不确定，实际表现就是游戏认为"不在店内"，
于是不显示「店内マッチング」分类（该分类是 id=198，图标 `UI_CMN_TabTitle_NetworkBattle`，
正常排在分类栏第 10 位："全曲" 右边、"宴会場" 左边）。

AquaMai 在该栏目的说明里已经写明：「如果要配置店内招募的话，应该要把这个关闭」。

修复（`AquaMai.toml`，注意注释掉无效，必须写 `Disabled = true`）：

```toml
[GameSettings.ForceAsServer]
Disabled = true
```

已执行，原文件备份为 `AquaMai.toml.bak-20261003-210125`。**朋友那边也要改这一条。**

## 第三个根因（最终确认）：没在 Test 模式里设置基准机

即使 DLL 统一、ForceAsServer 关掉，选曲界面仍然**没有「店内マッチング」分类**。

回头翻当初下载的 `NyanLink v2.0.0rev1.7z`，里面的《2.0.0 版本说明.txt》写着：

> 使用方法：将压缩包解压至 `Sinmai.exe` 同目录，启动游戏，
> **在 Test 模式中像图片那样设置基准机**。

包里附的 `基准机设置.jpg` 显示的是 Test 模式「ゲーム設定」页，两项都要改：

| 项目 | 要设成 |
| --- | --- |
| 店内マッチングの設定 | ON |
| グループ内基準機の設定 | 基準機 |

**这才是分类不出现的真正原因。** 之前换 DLL、关 ForceAsServer 都是必要但不充分的条件。

进 Test 模式的方法：按住 `F1`（`segatools.ini` 里 `[io4] test=0x70`，0x70 = F1）。

（当时拍的截图没随本仓库分发，那两项在「ゲーム設定」页里很好找。）

> 另外，该版本说明还提到「旧版客户端依然可以连接新版服务端并正常一起游玩」，
> 也就是说两边 DLL 不一致可能并不会直接导致加入失败。不过两边用同一份仍然是更稳的做法。

## 第五轮：反汇编找到真正的标签栏数据源（2026-10-04）

### 手段

扩展了 `tools/il.py`（新增 `type` / `methods` / `fields` 子命令，支持 `IL_ASSEMBLY` 换目标），
反汇编游戏本体的 `Assembly-CSharp.dll`，并顺带反汇编了 NyanLink 的客户端 mod `WorldLink.dll`
（NyanLink 官方客户端 mod）看它到底改了什么。

### 结论：上一轮的方向是错的

`MusicSelectProcess.GetGenreTexture` / `GetGenreTextureList` 是**歌曲封面缩略图**，
和标签栏无关（上一轮把调用者当成了「画标签格的地方」，其实那是 `GenreSelectChainList`
的大卡片面板）。

真正的底部标签栏链路：

```
Monitor.MusicSelectMonitor._genreTabController  (.GenreSelectController : .TabController)
  → .TabController._tab                         (.SelectorTab)
      → .SelectorTab._tabDatas                  List<TabDataBase>  ← 画格子的数据
```

`_tabDatas` **只在 `MusicSelectMonitor.OnStartMusicSelect()` 里生成一次**：

```csharp
var list = new List<TabDataBase>();
foreach (var d in _musicSelect.GenreSelectDataList[monitor])
    list.Add(new TabDataBase(getTabColor(d), GetTabSprite(d), getTabString(d), ""));
_genreTabController.SortType2Genre(list, 0);       // -> .TabController.Set -> _tab.SetData
_genreTabController.Change(_musicSelect.CurrentCategorySelect);
```

`.SelectorTab.UpdateTab(index)` 是个环形轮播：中间格显示 `_tabDatas[index]`，
左右格显示 `index±1±2…`。**`_tabDatas` 里没有的项，怎么滚都不会出现。**

三条关键代码事实：

| 事实 | 位置 |
| --- | --- |
| 标签栏快照 = `_tabDatas`，只在 `OnStartMusicSelect()` 生成 | `Monitor.MusicSelectMonitor.OnStartMusicSelect` (IL 872375–872541) |
| 滚动边界 = `CategoryNameList.Count`（不是 genre 数据条数） | `Process.SubSequence.MusicSelectSequence.CategoryScrollRight/Left` |
| 名字/数据/计数本是一起更新的，只有 `reinputConnectCombineData` 漏了名字 | `ExtraMusic` 末尾条件块 + `ExtraCategoryName` 末尾 |

### 根因

1. 进选曲界面时 `OnStartMusicSelect()` 已经按当时的 `_genreSelectDataList` 拍好 `_tabDatas`
   —— 那时招募数据还没来（`_currentExtraCategoryCount=4`，198 不在快照里）。
2. 之后 mod 的 `PartyExec → reinputConnectCombineData` 把 198 塞进 `_genreSelectDataList`，
   **但没有任何代码重拍 `_tabDatas`**。
3. 同一路径也**没补 `CategoryNameList`**，于是滚动边界比数据条数少 1，最后一格永远够不到。

这也解释了之前四次修补全部无效：它们都没碰到 `_tabDatas`（数据源根本不是那两份名单）。
顺带确认 `IsConnectCategoryEnable` 在 1.70 里是个死标志（全程序集无人读），置真没用。

### 修复（已写进 `tools/InStoreMatch.cs` v2，待编译实测）

- **A. 重拍标签栏**：检测到 `_genreSelectDataList` 里有 198 时，
  用游戏自己的方式重建 `_tabDatas`（`List<TabDataBase>` → `SortType2Genre` → `Change`）
- **B. 补滚动边界**：`CategoryNameList` 比数据少项时补上「店内マッチング」

触发点：`reinputConnectCombineData` / `SetConnectData` 的 Postfix + `OnUpdate` 每帧对账。

2. 分类栏出现「店内マッチング」（图标 `UI_CMN_TabTitle_NetworkBattle`）
3. 能滚到它、点进去能看到对方的房间并加入

## 第七轮：「ジャンル」面板里那张大卡片也是缺的（2026-10-04 深夜）

用户指出：标签栏虽然好了，但按「ジャンル」打开的那个面板里，**中间那张大卡片是空的**
（照片里能看到：左边 maimai、中间偏左 オンゲキ＆CHUNITHM、右侧整片空白）。

### 原因：游戏主动不画这张卡片

`Monitor.MusicSelect.ChainList.GenreSelectChainList.SetObjectData`（画大卡片的地方）开头：

```
local0 = SelectProcess.GetGenreSelectData(MonitorIndex, rel)      // 该格的分类数据
if (SelectProcess.GetCategoryName(MonitorIndex, rel)
        == DataManager.GetMusicGenre(198).genreName)              // 名字 == 「店内マッチング」
    local0 = null
...
if (local0 == null) { Remove(card); return false; }               // 卡片就不生成了
```

`GetCategoryName` → `GetMusicCategoryNameFromGenreIndex`（把 `CurrentCategorySelect + rel`
用 `_combineMusicDataList.Count` 回绕后取 `CategoryNameList[...]`）。
所以只要这一格算出来是「店内マッチング」，游戏就把卡片删掉——本体行为，不是注入造成的。
卡片不生 → 中间空一格，整排卡片看着"偏半格"。

`GetCategoryName` 在全程序集只有 4 个调用方：
`GenreSelectChainList.SetObjectData`、`MusicSelectChainList.DeployMusicList` / `Next`（决定
分隔线 `GetSeparate`）、`CategoryTabController.GetTagName`（显示用）。

### 对策（v2.1 新增 `ShowGenreCard` 开关）

挂 `MusicSelectProcess.GetCategoryName` 的 Postfix：返回值等于「店内マッチング」时
后面缀一个**零宽空格**（U+200B）。屏幕上完全看不出区别，但那个 `==` 判断不再成立，
卡片就会被正常生成。默认开启，出问题把这个开关改 false 即可。

## 第八轮：三个"缺按钮"全是本体自己写死的（2026-10-04 深夜）

后来的照片证明大卡片已经出来了（第三张「店内マッチング 新曲数1」），剩下的是按钮。
把三处代码都翻出来后，结论是**本体就是这么设计的**：

| 现象 | 本体代码 | 说明 |
| --- | --- | --- |
| 「店内マッチング」里没有 BACK | `MusicSelectSequence.IsBackEnable() => !IsConnectionFolder(0)` | 联机分类里**故意不给** BACK |
| 没有招募时没有 NEXT | `MusicSelectSequence.IsNextEnable()`：在联机分类里要求 `RecruitData != null` 且 `CanPlayMusic()` | 有招募才给 NEXT ✓ |
| 「ジャンル」面板站在 オンゲキ（倒数第二格）时没有右箭头 | `GenreSelectSequence.CheckButton`：`SetVisibleButton(CurrentCategorySelect + 1 != count, Button02)`，非 freedom 模式 `count` 还要 `-1` | 公式默认最后一格是占位分类，结果把「店内マッチング」也排除了 |

`IsConnectionFolder(musicIndex)` 的实现是 `GetMusicCategoryNameFromMusicIndex(musicIndex)
.Contains(GetMusicGenre(198).genreName)`，而后者最终返回 `CategoryNameList[分类下标]`，
所以「当前分类是不是店内マッチング」靠的就是我们补进 `CategoryNameList` 的那个名字。

### 对策（v2.2 三个开关，默认全开）

- `ShowRightArrow`：Postfix `GenreSelectSequence.CheckButton`，`CurrentCategorySelect + 1 <
  CombineMusicDataList.Count` 时强制点亮 Button02（右箭头）
- `ShowBackButton`：Postfix `MusicSelectSequence.IsBackEnable`，在联机分类里把结果改回 true
- 按钮 id 是全局枚举 `ButtonSetting`：`2`=右箭头 `3`=NEXT `4`=BACK `5`=左箭头
  （`Monitor.SetVisibleButton(bool, ButtonSetting)`，签名 blob `2002010211b624`）

⚠️ 这两个是**覆盖本体设计**，不是修 bug。不喜欢就把开关改回 false。

### v2.3 修正：右箭头补丁的边界写错了

第一版补丁沿用了本体那个被减过 1 的 `count`，结果变成"倒数第二格藏箭头、最后一格反而显示"，
和期望正好相反。正确做法是按**真实分类数**重算，并且该藏的时候要主动收掉：

```
SetButton(Button02, 当前下标 + 1 < 真实分类数)
```

于是：オンゲキ＆CHUNITHM（倒数第二）→ 左右箭头都有；店内マッチング（最后一格）→ 只有左箭头。
同时把 4 个开关从 `const bool` 改成 `static readonly bool`，CS0162 那条"无法访问的代码"警告也没了。

### v2.4：箭头能点动了（显示和响应是两套判断）

v2.3 把箭头显示修对了，但用户反馈"有右箭头、点了没反应"。查出来是**另一处同样的 off-by-one**：

| 管什么 | 位置 | 判断 |
| --- | --- | --- |
| 显示 | `GenreSelectSequence.CheckButton` | `SetVisibleButton(CurrentCategorySelect + 1 != count, Button02)` |
| 响应 | `GenreSelectSequence.Update`（输入处理） | `if (CurrentCategorySelect + 1 >= count) 直接跳过` |

两处都先做 `count = CombineMusicDataList.Count; if (!IsFreedomMode) count--;`，
于是站在倒数第二格（下标 10、count 变 11）时：箭头被藏过又被我们补回来，但**按下仍然被跳过**。

修法：`GameManager.<IsFreedomMode>k__BackingField` 是静态字段，而这两处判断的 freedom
只在 `GenreSelectSequence.Update` 这一次调用里用到，所以

- `Prefix`：临时把该字段置 true（相当于"按真实分类数算"）
- `Finalizer`：无论正常返回还是抛异常，立刻还原原来的值

配合 `CheckButton` 那边已有的补丁，显示与响应就一致了：オンゲキ 左右都能点，店内マッチング只有左箭头。
